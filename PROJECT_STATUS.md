# Project Status: Vela / Clinicare

Last updated: 2026-07-06

## Product Overview

Vela / Clinicare is a SaaS workspace for clinics and appointment-based businesses. The app helps a clinic manage onboarding, branding, clients, staff, bookings, WhatsApp conversations, reminders, reports, and AI-assisted performance insights from one workspace.

The core product direction is customer-first: clinics should not need to understand Baileys, Twilio, Meta, Supabase, Prisma, or OpenAI. Provider complexity should stay behind simple product language and support-friendly states.

## Technical Stack

- Next.js 16.2.6 App Router with React 19.
- TypeScript, Tailwind CSS 4, shadcn-style UI components, Radix primitives, Lucide icons.
- Prisma with PostgreSQL via Supabase.
- Supabase Auth for email/password authentication and email confirmation.
- Vercel production deployment from Git.
- WhatsApp via Baileys, run in an isolated always-on worker (Kosovo pilot, non-PHI, disposable) behind the `sendMessage()` messaging seam; paired by QR from Settings, with webhook-based inbound inbox messaging. Twilio is reserved for SMS/phone and is not wired yet.
- OpenAI-backed analytics snapshots with rule-based fallback when AI is unavailable.

## Completed Features

- **Staff-thread admin-notify: closes the loop when a staff member's mobile activity needs the admin's attention (2026-07-06, PR #39, merged to main).** Previously, when a staff member's thread got new activity (most commonly the system message posted when a doctor cancels their own appointment via mobile), the admin had no indication short of opening that staff member's Messages tab on the off chance they checked. Added: an unread-message dot on the Staff Directory list row and on the staff detail page's Messages tab (`getStaffUnreadMessageCounts` in `lib/staff-data.ts`, DB-aggregated like the existing directory counts); a directory row with unread messages deep-links straight to `/staff/[id]?tab=messages`, and so does the dashboard's existing "Reply" toast (a second entry point to the same activity); cancelling now also creates a generic, non-PHI "Cancellation sent" `StaffNotification` confirming to the staff member that the admin was actually told. Shipped after a 3-round, 9-agent adversarial review (plus live browser/DB verification) that found real bugs a single self-review pass missed: a CSS bug (`flex` + `truncate` on an element holding a raw text node + sibling dot) that hid the unread indicator entirely for long staff names; the Messages-tab dot staying lit for the rest of a page's client session even after the admin read the messages (no client-state sync with the server-side mark-read); a misleading log message on a partial best-effort failure; and — most substantively — a genuine race in `ensureAdminThread` (`lib/mobile/inbox.ts`, non-atomic findFirst-then-create, predating this PR) that could create two `StaffThread` rows for one staff member, permanently stranding an unread count no UI path could ever clear. Fixed with a DB-level `@@unique([businessId, staffMemberId])` constraint + an atomic `upsert`, the only way to actually close a check-then-act race like this one — verified live by firing 10 truly concurrent `ensureAdminThread` calls (all 10 resolved to one row) and by directly querying `pg_constraint`/attempting a real duplicate insert against the live database. A follow-up review of that fix itself then caught one more edge: Prisma's `upsert` can still throw `P2002` under true first-contact concurrency even though the constraint prevents the duplicate row; closed with the same catch-and-refetch pattern `lib/mobile/clock.ts`'s `openTimeEntryIfAbsent` already uses for its own concurrent check-in race. Verified throughout with `tsc --noEmit`, `npm run lint`, `npx vitest run` (119 tests, including new coverage for `buildStaffDirectoryRecord`/`buildStaffViewFromRecords`'s unread-count params), `npm run build`, `npm audit --omit=dev` (0 vulnerabilities), and repeated signed-in browser QA (precise DOM/geometry checks, not just screenshots).

Cause: `@upstash/redis` defaults to 5 retries with `Math.exp(n)*50`ms backoff ≈ 4.3s of sleep before falling back to the in-memory limiter. Consequences: **the mobile app is effectively unusable in production**, and rate limiting IS degraded to per-instance counters exactly as this item warned. Code side is mitigated (`lib/redis.ts` caps a fault at ~500ms). **RESOLVED 2026-08-28:** the root cause was Upstash **archiving the free-tier database for inactivity** while the env vars stayed behind. Virginia round trip, since the replacement sits in `us-east-1` while the app serves from `fra1`. Moving it to `eu-central-1` would recover that ~150ms. Note the failure recurs by design: Upstash archives idle free-tier databases, and pilot traffic is idle by nature — the `lib/redis.ts` cap is what keeps the next archive cheap instead of a silent 4.7s regression. A circuit breaker (3 consecutive failures -> 30s open, single-flight half-open probe) now bounds the *outage*, not just each call, so callers fall back to in-memory instead of every request re-paying the timeout; `src/lib/redis.test.ts` pins the per-call-fresh `signal` invariant, which a static `AbortSignal` would silently break for the life of every warm instance.
